# Финальная сдача: маршруты, ограничения и проверка

## Что осталось неизменным

Профиль сдачи — `config/balanced.json`, режим `balanced_minimax`. Ни hard-правила, ни веса, ни порядок выбора не менялись после исходной сдачи 90 операций в коммите `a225582a4002c672c42efd1017d5f5cb834e352e`. Последняя доработка добавляет аналитику и её проверку, не подменяет политику по результатам уже увиденной очереди.

Два обязательных файла находятся в корне ветки `main`: `routing_decisions_test.json` и `routing_report_test.json`. Исходная очередь организаторов хранится локально и не входит в Git. Все 90 ответов `approved` относятся к явно указанной симуляции `approve`, а не к реальным переводам или измеренной конверсии.

Поле `raw_target_deviation_l1_pp` суммирует модули округлённых отклонений трёх внешних провайдеров: **61,11 п.п.** Знаменатель — вся очередь, включая fallback. Если отдельно включить в сумму отклонение fallback и считать без промежуточного округления, получится **65,56 п.п.** Эти два определения нельзя смешивать. Ни одно не является процентом неуспешных выплат.

## Что действительно ограничено данными

Верхнеуровневый раздел `capacity_explanation` рассчитывается из исходного снимка, очереди и окончательных решений. Денежная арифметика сумм и сравнения лимитов выполняется в копейках.

- **Payflow.** На старте использовано 2 900 000 из 3 000 000 ₽: остаётся 100 000 ₽. В очереди ему назначено 99 400 ₽ — **99,4% начального остатка**, а не 99,4% полного дневного лимита. Итоговая загрузка дневного лимита — 99,98%. Даже 19 самых дешёвых операций из допускаемого отдельным провайдером набора требуют 105 200 ₽; 18 требуют 90 200 ₽. Следовательно, при данном снимке отдельный потолок — **не больше 18 операций**, то есть 20% очереди, ниже цели 35%.
- **Vipay.** Индивидуальным правилам соответствуют 31 из 90 операций; их общий объём не исчерпывает свободный дневной бюджет. Выбрано 29 — **93,55% отдельного потолка**. Это не утверждение, что текущая политика оптимальна.
- **Quickpay.** Широкое покрытие банков, диапазон суммы до 200 000 ₽ и больший свободный бюджет позволяют принимать значительную часть операций, не проходящих через других внешних провайдеров. Он не единственный провайдер с положительным остатком лимита; четыре перехода в fallback по-прежнему проверяются по конкретному состоянию в момент выбора.

Потолки вычисляются **для каждого провайдера отдельно** в ослабленной задаче: временная занятость и RPM не сужают верхнюю границу. Это безопасная верхняя граница возможностей, а не обещание одновременно получить все такие назначения. Стартовые правила, дневной бюджет и ограничения одной операции сохраняются. Если были изменения правил, отказы, таймауты или нарушены предпосылки статического дня, численные потолки не выдаются.

**Глобальный минимум L1 для этой очереди не доказан.** В частности, утверждать «структурный минимум около 57 п.п.» нельзя: допустимая альтернативная политика уже дала меньше. Нельзя также считать каждый зарегистрированный отказ по дневному лимиту исключительно следствием лимита: одна операция может одновременно нарушать несколько правил, а `HardGate` возвращает первую причину.

## Отдельное сравнение конфигураций

```bash
ruby scripts/compare_policies.rb --queue operations_queue_test.json --output outputs/policy-review.json
```

Скрипт запускает настоящий движок и строгий валидатор дважды. Во втором профиле меняются только `profile` и `selection_mode=conversion_first`; остальные параметры копируются из balanced, цели объёма не придумываются. Оба прогона используют `approve`. Скрипт не меняет файлы сдачи, основной профиль или правила провайдеров.

На этой очереди альтернативный порядок даёт **31 / 10 / 45 / 4** и **54,45 п.п.** по округлённой метрике отчёта. Без промежуточного округления внешний L1 — 54,444444… п.п. На публичной очереди оба профиля дают 4 / 3 / 3 / 0. Машиночитаемая запись со связью с хешами входов: [evidence/policy-review.json](evidence/policy-review.json). Использовать её численные результаты можно только для соответствующих входов.

Это **ретроспективное сравнение после просмотра очереди**, не независимая оценка на новых данных и не обещание будущего улучшения. Приоритет конверсии меняет компромисс: в `conversion_first` общий взвешенный вторичный балл не участвует в ранжировании; порядок задают конверсия, долг целей, нагрузка и приоритет. Поэтому улучшение долей в одном прогоне не означает превосходства по всем требованиям. Настройка предложена оператору для анализа, не включена автоматически.

## Проверить сдачу

Финальный прогон `LANG=C LC_ALL=C rake release submit`: **230 тестов / 6597 проверок, без ошибок**; строгая валидация 90/90, исполняемая матрица 31/31, отдельный публичный валидатор 29/29, доля производственного Ruby-кода 76,07%, lint и сборка пройдены. Повторная генерация дала побайтово одинаковые файлы. Решения совпадают с исходной сдачей; в отчёте изменились только новая аналитика ёмкости, её маркер проверки и одна рекомендация. Отдельный скан всех 96 уникальных строк реквизитов не обнаружил утечек в двух файлах сдачи, демо или сохранённом сравнении.

После получения очереди и изменения исходников используется полный путь; старая preflight-квитанция не подходит:

```bash
rake release submit
ruby scripts/compare_policies.rb --queue operations_queue_test.json --output outputs/policy-review.json
```

Затем проверить diff, закоммитить исходники и оба обязательных JSON, отправить ветку `main` и выполнить:

```bash
rake submission_git
git rev-parse HEAD
git ls-remote origin refs/heads/main
```

`submission_git` подтверждает локальные закоммиченные артефакты и их соответствие очереди; совпадение последней пары хешей отдельно подтверждает публикацию. Доступ экспертов к приватному репозиторию — отдельная настройка владельца; существование ссылки само по себе доступа не предоставляет.
