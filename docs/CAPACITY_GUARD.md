# Сохранение последнего внешнего маршрута

## Продуктовая идея

Универсальный провайдер нужен не одинаково всем выплатам. Для части заявок он один из трёх вариантов, для другой части — единственный внешний вариант. Поэтому остаток его лимита имеет ценность не только сам по себе, но и через типы выплат, которые без него останутся лишь с fallback.

В официальной history 100 строк. Если проверить формы этих заявок на исходном текущем снимке провайдеров, 37 имеют единственный внешний маршрут — quickpay. Это свойство предоставленного примера, не прогноз доли будущих заявок. Дополнительных будущих операций роутеру не передаём.

Теперь есть два связанных механизма:

1. `CapacityGuard` в runtime проверяет, какие исторические типы заявок потеряют последний внешний маршрут после резервирования текущего платежа. Может выбрать другого допустимого кандидата в пределах явно заданного компромисса.
2. `CapacityLab` сам перебирает небольшое семейство стресс-сценариев и ищет воспроизводимый пример, где включение защиты уменьшает число fallback. Он обязательно показывает и ветку без ожидаемой сложной заявки, чтобы не скрыть цену защиты.

## Запуск

```bash
bin/pulseproof lab
```

Сохраняет отдельный `outputs/capacity-lab.json`; не изменяет исходных провайдеров и конкурсных выходов. Лаборатория использует банк/сумму/совместимость из истории, но порядок заявок и уменьшенный остаток лимита искусственные. Это не скрытая очередь и не реальный денежный результат.

Опциональный runtime-профиль:

```bash
bin/pulseproof run --policy config/resilience.json --queue data/operations_queue_10.json --decisions outputs/resilience-decisions.json --report outputs/resilience-report.json
```

Основной balanced-профиль не заменён. Сначала следует оценить бизнес-компромисс, а не автоматически включать защиту всем.

## Найденный пример

На исходных правилах, но с искусственно уменьшенным остатком quickpay до 120 000 ₽, поиск нашёл такую последовательность:

| Поступающая выплата | Balanced | С защитой |
| --- | --- | --- |
| 1 500 ₽, alfa | payflow | payflow |
| 1 500 ₽, alfa | quickpay | payflow |
| 120 000 ₽, alfa | spacepayments | quickpay |

Во втором решении runtime ещё не видел третью выплату. Он видел лишь исторические формы заявок на 120 000 ₽ и то, что резерв 1 500 ₽ оставит 118 500 ₽, лишив такие формы последнего внешнего маршрута. В объяснении сохраняются потерянные исторические группы и конкретное hard-правило, например `daily_amount_limit_exceeded`.

Поиск проверил 97 сценариев до этого примера. Минимальность относится только к объявленному семейству: повторяющиеся общие заявки, затем одна исключительная; это не глобальный поиск всех возможных последовательностей.

Цена в данном маленьком искусственном примере:

- Если крупная заявка приходит: fallback 1 → 0, но L1-отклонение от внешних целей по количеству 50 → 80 п.п.
- Если она не приходит: fallback остаётся 0, а L1-отклонение ухудшается 80 → 130 п.п.

L1 — сумма абсолютных отклонений по провайдерам, поэтому она может превышать 100 п.п. Мы не трактуем номинал выплаты как прибыль и не придумываем стоимость fallback: в исходных данных fallback даже имеет выгодные показатели комиссии и конверсии. Сокращение fallback — отдельный бизнес-показатель, не доказательство большей прибыли или более высокого балла жюри.

## Что ограничивает вмешательство

Защита работает поверх hard-фильтра и исходного ранжирования. Она не открывает запрещённые маршруты и не вызывает банки при сравнении вариантов.

- `min_samples: 20`: при недостатке истории ничего не меняет.
- `max_samples: 1000`: ограничивает модель исторических форм.
- `max_primary_regret_delta: 0.25`: допустимое увеличение внутренней нормированной count/volume-оценки относительно исходного победителя.
- `max_conversion_drop: 0.02`: допустимое уменьшение используемой оценки конверсии.

Это локальные бюджеты решения, **не гарантия ограничения итогового отклонения долей на 25 п.п. или максимальной потери реальной конверсии на 2 п.п.** Цена, нагрузка и иные факторы сохраняются в исходном ранжировании, но отдельного жёсткого бюджета на комиссию этот прототип не задаёт.

Если ни один разрешённый альтернативный кандидат не сохраняет больше исторических форм, остаётся исходный выбор. При равенстве сохраняется исходный порядок. Переключение и контрфактическая проверка отражаются в proof capsule и `capacity_protection` отчёта.

## Данные и сложность

В модели только bank, card_brand, amount и частота; нет телефонов, реквизитов, operation_id из history и выбранного исторического провайдера. Строки после разрешённого снимка не участвуют. Модель заморожена на исходном cutoff сессии; автоматического обучения новым частотам пока нет. Доступность исторических форм пересчитывается по текущим правилам, резервам и счётчикам.

Для одной операции выполняются проверки по числу исторических групп и провайдеров. Гипотетические резервы живут только в копиях состояния. При исключении одного выбранного провайдера потерять последний маршрут могут лишь группы, которые до этого имели ровно один вариант; это сокращает повторные проверки.

Нет прогноза точной будущей очереди, заявления об оптимальности или поиска решений по текущей тестовой очереди внутри runtime. Историческая поддержка — индивидуальная проверка каждой формы, не доказательство возможности одновременно обслужить весь исторический поток. Временные ограничения отражают момент резервирования, а не обещание постоянной потери маршрута.

## Проверки

`test/capacity_guard_test.rb` проверяет сохранение маршрута, неизменность прошлого решения при добавлении suffix, отрицательный сценарий без сложной заявки, запрет вмешательства по бюджетам, отсутствие реальных мутаций при оценке, исключение будущей истории, переименование всех провайдеров, неизменность публичного результата и воспроизводимость лаборатории. Финальные лабораторные отчёты проходят независимый replay журнала.

После добавления прототипа полный `rake release` прошёл: 59 тестов, 245 assertions, 0 ошибок; публичный валидатор 29/29, проверка чувствительных значений, lint и сборка интерфейса также прошли. Новый режим не включён в основной сдаваемый профиль.

## Что уже стандартно на рынке

[Juspay Decision Engine](https://github.com/juspay/decision-engine) публично описывает правила, ранжирование по успешности и совместный учёт стоимости. [Hyperswitch](https://docs.hyperswitch.io/about-hyperswitch/payments-modules/intelligent-routing) описывает интеллектуальные стратегии и контрактные объёмы, а [его документация симулятора](https://github.com/juspay/hyperswitch-docs/blob/main/integration-guide/workflows/intelligent-routing/auth-rate-based-routing.md) — тестовые сценарии маршрутизации.

Поэтому ни скоринг, ни fallback, ни сам симулятор не заявляются как мировое изобретение. Предлагаемое отличие нашей демонстрации — конкретная зависимость между уникальной совместимостью и расходом лимита плюс автоматически найденный контрпример с обеими сторонами компромисса. Новизна относительно всех конкурентов хакатона не проверена.
