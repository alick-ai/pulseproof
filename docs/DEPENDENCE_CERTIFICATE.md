# Что можно утверждать о каскаде при неизвестной зависимости отказов

Модуль реализован в `DependenceCertificate`; `DependenceVerifier` независимо проверяет его арифметику. Он добавляет аналитические данные к экспериментальному planner, **не меняет выбор, глубину цепочки, исполнение или профиль сдачи balanced**.

## Посмотреть на публичном примере

```bash
bin/pulseproof run --policy config/planner.json --queue data/operations_queue_10.json --decisions outputs/planner-decisions.json --report outputs/planner-report.json
bin/pulseproof validate --policy config/planner.json --queue data/operations_queue_10.json --decisions outputs/planner-decisions.json --report outputs/planner-report.json
bin/pulseproof explain op_101 --decisions outputs/planner-decisions.json --report outputs/planner-report.json
```

`explain` проверяет план до печати. Подмена границы даже на один соседний Float, удаление сертификата с сохранением нового маркера версии или ложное утверждение об оптимальности порядка приводят к ошибке, а не к красивому объяснению.

На публичном op_101 при неизменных входах: независимый расчёт полного отказа ≈ **0.063505%**, но достижимый интервал при неизвестной зависимости — **0–10%**. Интервал успеха — **90–100%**. Здесь успех означает модельное терминальное принятие, не подтверждённое зачисление денег получателю.

Нижнюю границу задаёт `spacepayments` с p = 0.9. Внешние провайдеры повышают ожидание в независимой модели, но **не повышают нижнюю границу успешности относительно одного fallback**: прирост равен 0 п.п. Это не утверждение о нулевой ценности внешних провайдеров вообще и не обещание настоящей банковской гарантии.

## Точная постановка

Берём полный каскад из текущего замороженного снимка. Каждый провайдер имеет потенциальный бинарный исход; переданные оценки pᵢ условно принимаются за маргинальные вероятности успеха этих исходов. Нет pending, ограничения и состав остаются фиксированными, после каждого отказа доступна следующая попытка. Тогда успех каскада — объединение событий успеха отдельных провайдеров.

При qᵢ = 1 − pᵢ:

```text
P(успех)       ∈ [maxᵢ pᵢ, min(1, Σpᵢ)]
P(все отказали) ∈ [max(0, Σqᵢ − (n−1)), minᵢ qᵢ]
```

Каждый конец этого интервала достижим при соответствующем совместном распределении. Вложенные события успеха достигают нижней границы успеха; максимально разнесённые события — верхней. Никакой оценки корреляций для этих событийных границ не нужно. Формула и многомерная оговорка: [Erdely, A Subcopula Characterization of Dependence for the Multivariate Bernoulli Distribution, уравнение 3](https://link.springer.com/article/10.1007/s44199-025-00157-4).

Это точечная достижимость концов событийного интервала. Она **не** означает, что один и тот же закон одновременно реализует экстремумы стоимости, задержки, pending и атрибуции. Подставлять отдельные худшие границы во все члены целевой функции нельзя.

JSON содержит точные рациональные концы `exact_bounds` для экспортированных Float-маргиналов и округлённые числовые поля для чтения. Независимый ориентир сертификата вычисляется с рациональными дополнениями 1 − p. Ориентир старого оптимизатора использует отдельно округлённые Float-продолжения, поэтому последнее машинное разрядное место может различаться. Сам оптимизатор не изменён.

## Где сертификат неприменим

- Любой tᵢ > 0: ожидание статуса блокирует поздние попытки. Объединение их потенциальных успехов уже не описывает исполненный успех. Возвращается `not_applicable / pending_blocks_later_attempts`, **без числовых границ**. Проверка консервативная: даже потенциально недостижимый pending исключает этот сертификат.
- Пустая цепочка: `not_applicable / empty_chain`.
- Неполная цепочка, повтор провайдера, недопустимые или нечисловые вероятности: ошибка, без сертификата.
- Фактическое перепланирование после отказа, изменение лимита/правил между попытками, ошибка оценок p, отбор исторических наблюдений: вне доказанного утверждения. Маргиналы здесь заданы, а не статистически подтверждены.

Фраза «без предположений о зависимости» не означает «без предположений о данных». Это не доверительный интервал и не оценка качества всей очереди. Ошибка самих p и зависимость потенциальных исходов — разные неопределённости; их совместная оптимизация не реализована.

## Почему это не сертификат оптимального порядка

В текущем планировщике `reach` вычисляется из фиксированных per-provider вероятностей, не условных вероятностей после конкретного набора отказов. Само произведение не проблема: цепное правило тоже использует произведение, но его множители должны соответствовать условному распределению данного префикса.

Уже сейчас от `reach` зависят ожидаемые попытки, задержка, конечная атрибуция и бизнес-штрафы. Поэтому неизвестная зависимость способна изменить предпочтительный порядок при тех же маргиналах.

Исполняемый регрессионный пример: p_A = 0.8, p_B = p_C = 0.75, p_S = 0.9; массы совместных отказов A/B/C — `{A,B}: 0.10`, `{A,C}: 0.10`, `{B}: 0.15`, `{C}: 0.15`, `{}: 0.50`. Маргиналы сохраняются; fallback S в этом совместном сценарии не достигается.

| Порядок | E[попытки], независимость | E[попытки], указанный совместный закон |
| --- | ---: | ---: |
| A → B → C → S | 1.2625 | 1.30 |
| B → C → A → S | 1.3250 | 1.25 |

Выбор переворачивается. Интервал Фреше успеха одинаков для этих порядков и не выбирает между ними. Это доказательство возможности переворота, **не свидетельство ошибочного выбора на реальном op_101**.

При t = 0 и одинаковом составе инвариантен к перестановке член полного отказа. При фиксированном последнем fallback инвариантна и вероятность его достижения при перестановке внешних провайдеров. Нулевые остальные члены в отдельном отчёте — свойство снимка. При t > 0 член `unresolved_or_failed` может стать порядково-зависимым; при изменении состава/глубины может измениться и полный отказ. Даже без этих изменений остальные различающие члены уже зависят от модели совместных исходов.

## Интеграция и проверка

В каждом `outcome_plan.dependence_certificate` — границы именно его полной цепочки, исходные p, причины неприменимости, все провайдеры, определяющие нижнюю границу, и сравнение с одним fallback. Поле `optimization.dependence_certificate_version = 1` требует наличия сертификата. Его удаление не превращает новый отчёт молча в проверенный старый. Старые отчёты без обоих полей остаются читаемыми; `explain` явно сообщает отсутствие новых границ. Это не криптографическая защита от замены всего отчёта.

`PlanVerifier` сначала связывает модель с сохранённым снимком. Затем `DependenceVerifier` восстанавливает границы через пересечение отказов, не вызывая производителя сертификата или оптимизатор; проверяются числа, точные дроби, версия и ограничения утверждения.

`outcome_planning.dependence_certificates` считает покрытие **по снимкам перед попытками**, не по альтернативным цепочкам и не по операциям. Runtime-пути только с fallback обходят planner и отмечены как `without_model_certificate`; standalone-модуль умеет вычислить вырожденный интервал для одного fallback. Нет ложного «100% покрытия» и усреднения несопоставимых гарантий по очереди.

Тесты охватывают достижимость обоих концов на конечном пространстве исходов, произвольные совместные распределения, нулевые/единичные p, ничьи, отсутствие fallback, pending, точные дроби, подмену JSON, старые отчёты, CLI и отсутствие влияния сертификата на ранжирование.

Проверка текущей версии: 188 тестов / 6306 assertions без ошибок; locale-регрессии внутри набора запускают CLI с C-, POSIX-, UTF-8-локалью и без переменных локали. Полный `rake release` прошёл; исполняемая матрица требований — 31/31, официальный публичный balanced — 29/29. Решения и все проверенные `chain / objective / raw_metrics / terms / all_failed_probability` на публичной очереди точно совпали с отчётом до модуля. Обратное переключение op_101 сохранилось на 0.7985512111061965, соседний меньший Float по-прежнему выбирает payflow. Полный plan-lab для этой аналитической доработки заново не запускался.

## Что не заявляем

Нет нового robust/minimax-роутера, оптимизации глубины, автоматической смены политики или доказанного прироста конверсии. Модуль и примеры выбраны **после просмотра существующих результатов plan-lab**; это ретроспективная аналитическая доработка и регрессионная проверка, не заранее зарегистрированное исследование и не новый holdout. Сценарный поиск и проверка новой политики на заранее удержанных условиях остаются отдельной работой.
