# Цели объёма и недоступность провайдера

В начале `routing_report_test.json` находятся `volume_goal_status` и
`unavailable_goal_handling`. Оба раздела описывают уже выполненный прогон.
Они не меняют выбор, доли, лимиты или веса роутера.

## Распределение по объёму

`volume_distribution` показывает сумму, фактическую долю, цель, отклонение,
источник цели и `null_reason` для каждого провайдера. Сумма относится к
итоговому `selected_provider`, включая предварительное назначение при pending.
Знаменатель — сумма операций проверяемой очереди; история и дневной оборот в него
не добавляются. Это распределение назначений, а не банковская сверка зачислений.

В исходных `data/providers.json` нет `volume_share_pct`, в `balanced` нет
`volume_targets`. Поэтому цель и отклонение равны `null`, а
`volume_goal_status` прямо объясняет причину. Вес контроллера `0.8` настроен,
но без цели не создаёт давления по объёму. Суммарная ошибка объёмных целей тоже
`null`, поскольку отсутствие цели нельзя выдавать за нулевую ошибку.

Для самостоятельной проверки предусмотрен `config/volume_demo.json`:

```bash
bin/pulseproof run --policy config/volume_demo.json --queue data/operations_queue_10.json --decisions outputs/volume-demo-decisions.json --report outputs/volume-demo-report.json
ruby -Itest test/goal_reporting_test.rb
rake evidence
```

Профиль отличается от `balanced` только названием, пояснением и явно заданными
объёмными целями. Числа 25/10/65 выбраны для демонстрации на уже известной
публичной очереди. Это не цели организаторов, не независимый бенчмарк и не
рекомендация для сдачи.

| Провайдер | Иллюстративная цель объёма | Фактическая доля | Отклонение |
| --- | ---: | ---: | ---: |
| vipay | 25% | 26.44% | +1.44 п.п. |
| payflow | 10% | 10.58% | +0.58 п.п. |
| quickpay | 65% | 62.99% | −2.01 п.п. |

При тех же hard-правилах операция `op_102` меняет маршрут `payflow → quickpay`.
Изменение цели реально влияет на решение. Есть и компромисс: ошибка долей
по количеству растёт с 10 до 30 п.п. L1. Профиль демонстрирует возможность
задавать объёмную цель, а не превосходство над `balanced` по всем критериям.
Округлённые доли могут давать в сумме 100.01%.

Случай `soft_volume` в исполняемой матрице дополнительно изолирует один фактор:
на двух допустимых провайдерах меняет только объёмную цель 80/20 → 20/80
и проверяет переключение победителя. Отчёт ссылается на эту команду и случай;
он не запускает всю матрицу внутри обработки финальной очереди.

Семантика источников совпадает с контроллером:

- При наличии `profile.volume_targets` он полностью заменяет цели из
  провайдеров; пропущенный внешний провайдер получает 0.
- Без этого поля берутся заданные `providers.volume_share_pct`.
- Положительная сумма целей нормализуется до 100% среди внешних провайдеров.
  `configured_target_pct` сохраняет исходное число; `target_pct` показывает
  эффективную цель контроллера.
- Пустой или нулевой override отключает цель. Fallback не включается в неё.
- В runtime используется последняя цель, с которой действительно начислялся
  долг операции. Обновление конфига после последней операции не переписывает
  задним числом целевые доли прогона. Если цели менялись в ходе очереди,
  сравнение с последней целью не является оценкой выполнения всех прошлых целей.

## Поведение при недоступности

`unavailable_goal_handling.providers` показывает для каждого внешнего провайдера
число недопустимых операций, причины, несколько ссылок по `operation_id` на
полные `proof_capsules`, итоговые назначения после исключения и исходный
бизнес-долг рядом с ограниченным управляющим долгом.

«Недоступен» означает недопустим для данной операции: например, банк вне списка
или сумма выше лимита. Это не утверждение об аварии. Отказ уже выбранного
провайдера учитывается в `provider_outcomes`; он не превращается в отдельное
hard-исключение в этой сводке. Каждая операция учитывается один раз по первой
оценке, даже если затем произошёл каскад или поздняя отмена.

В `balanced` `redistribute_unavailable` выключен: исходная доля остаётся целью,
выбор идёт среди допустимых провайдеров, управляющий долг ограничен по модулю
четырьмя операциями. Исходный бизнес-долг сохраняется отдельно. При включённой
опции перераспределяется только текущее начисление управляющего долга среди
допустимых; исходный бизнес-долг всё равно сохраняется.

После возврата в допустимые применяется `recovery_rate = 0.75`: эффективный
долг провайдера ограничивается максимумом долга остальных допустимых плюс 0.75.
Это ограничение давления на ранжирование, а не лимит запросов в секунду и
не гарантия точного попадания в конечные доли. Если другой кандидат отсутствует,
уменьшать долг не требуется.

На публичной очереди `payflow` недопустим для 6 операций: 4 раза из-за банка,
2 раза из-за суммы. Восстановление начинается дважды:

| Операция | Долг до ограничения | Эффективный долг | Что произошло |
| --- | ---: | ---: | --- |
| op_107 | 1.45 | 1.45 | Единственный допустимый кандидат; уменьшения нет |
| op_110 | 1.50 | 0.25 | Ограничение действительно уменьшило долг |

Отчёт отдельно считает входы в восстановление, ранжирования с флагом
восстановления и фактические уменьшения долга. Уменьшение долга само по себе
не доказывает смену победителя. Полные снимки сохранены в `proof_capsules`.
Число коротких примеров ограничено тремя на провайдера; агрегаты учитывают все
операции и попытки.

Регрессии проверяют также длительное отключение по `status`, включённое
перераспределение, нормализацию, частичные и нулевые цели, смену конфигурации,
пустую очередь, каскады и отсутствие изменений состояния при построении отчёта.
