# Адаптивный роутинг: что действительно меняется от опыта

## Проверяемое поведение

Без правки конфигурации роутер получает подтверждённые ответы, пересчитывает оценку качества конкретного сегмента и меняет следующие решения. Падение качества связки «провайдер × банк × карточная система × диапазон суммы» не понижает автоматически оценку этого провайдера для всех остальных выплат.

Это исполняемый Ruby-модуль, а не экранная анимация. Его можно включить в тот же потоковый runtime, который резервирует лимиты и обрабатывает поздние статусы. При этом банковского HTTP-адаптера в поставке нет: текущие прогоны используют симуляцию.

## Механизм

1. HardGate сначала исключает недопустимые маршруты. Обучение и проверочные попытки не обходят эти ограничения.
2. Для каждой связки хранятся последние 40 подтверждённых исходов. Успех имеет метку 1, подтверждённый отказ/отмена — 0. Это оценка принятия выплаты, не оценка окончательного денежного расчёта вне данного протокола.
3. Старый опыт теряет половину веса за 300 секунд. Априорная оценка берётся из текущего `conversion_24h` провайдера; история не добавляется повторно в этот prior.
4. Пока подтверждений мало, основным критерием остаётся балансировка количественных/объёмных целей. При сигнале ухудшения включается настроенный компромисс между качеством и отклонением от целей.
5. Для давно не проверявшегося ухудшившегося сегмента предусмотрена ограниченная повторная проверка небольшим платежом. Успехи и затухание старого опыта могут вернуть провайдера в обычный выбор; мгновенное обнаружение восстановления не гарантируется.
6. Итоговая доля считается по конечному провайдеру после каскада. Неудачная первая попытка не становится окончательной долей трафика.

### Оценка и порог

Для наблюдения возрастом `age` вес равен `2^(-age / 300)`. Пусть `n` — сумма весов, `s` — сумма весов успехов, `p` — текущая конверсия из снимка:

```text
alpha = 0.5 + 8 × p + s
beta  = 0.5 + 8 × (1 − p) + n − s
mean  = alpha / (alpha + beta)
sd    = sqrt(alpha × beta / ((alpha + beta)^2 × (alpha + beta + 1)))

degradation_signal = n >= 6 AND mean + 1.5 × sd < p − 0.10
```

Это Beta-оценка с затухающими дробными наблюдениями и эвристический порог, **не калиброванный доверительный интервал** и не доказанная вероятность аварии. Один случайный отказ не переключает режим. При сигнале текущий профиль использует weighted-sum; без сигнала сортирует сначала по отклонению от целей, затем по качеству и бизнес-факторам. Это не жёсткая гарантия конечного отклонения: в неизвестном потоке итог всё равно зависит от доступности и ответов.

Проверочные попытки допускаются только на каждой 20-й первой попытке в контексте, для суммы не выше 5000, после минимум 60 секунд без ответа этого сегмента, при отсутствии текущих резервов у провайдера и с ограничением дополнительного нормированного goal-regret 0.25. Если включён capacity guard, проверка также не должна ухудшать его оценку сохранённого покрытия. Это максимум 5% возможностей по числу операций контекста, не бюджет по деньгам и не доказанная максимальная потеря.

## Что не становится обучающей меткой

- Ответ провайдера, которого не выбирали: его исход неизвестен.
- Неразрешённый timeout: резерв остаётся, метки отказа нет.
- Повтор того же статуса для той же попытки: повторного обучения нет.
- Несогласованный или устаревший статус чужой попытки.
- Будущая история, ещё не доступный по времени ответ, история с отрицательной/нечисловой задержкой, несовместимыми банком/суммой/карточными правилами.

Для синхронного каскада доступность метки учитывает суммарную задержку уже выполненных попыток. Поздний статус используется с временем принятого события. Оценка для операции не использует метки с более поздним временем. Модель не принимает будущую очередь.

В журнал пишется `learning_observed` с operation/provider/attempt, исходом и временем. AuditReplay независимо проверяет связь метки с выбранной подтверждённой попыткой и отсутствие дублирования; StrictValidator сверяет количество меток и терминальных попыток. Это проверка происхождения меток, а не независимое воспроизведение всей математики оценки и не подписанная банковская квитанция.

## Воспроизводимый эксперимент

Из корня проекта:

```bash
bin/pulseproof learn-lab --lab-seeds 404,505,606 --lab-output outputs/adaptive-holdout-v2.json
```

Три сценария, три seed, три политики, по 240 операций: 27 отдельных прогонов. Во всех работают обычные Router, HardGate, Ledger и независимый валидатор. Сравниваются:

- `balanced` — исходный профиль сдачи;
- `fixed` — адаптивный профиль с теми же весами и prior, но без обучения и проверочных попыток;
- `adaptive` — этот же профиль с обучением.

Ответы имеют одинаковый потенциальный исход для пары операция/провайдер во всех политиках. Роутеру выдаётся только выбранный ответ. История пуста. Специально убраны банковские ограничения и увеличена дневная ёмкость, чтобы отдельно проверить реакцию на качество, а не исчерпание лимитов. Сумма всех операций 2000, банки чередуются, интервал 10 секунд. Среда — отдельный код; только она знает фазы и изменённые вероятности.

Результаты ниже — средние по seed 404, 505, 606. Успешность означает принятие **с первой попытки**, не окончательную конверсию после всех каскадов и не выручку.

| Сценарий | Balanced: успех, % | Fixed: успех, % | Adaptive: успех, % | Adaptive − balanced, п.п. | Ошибка долей L1: balanced → adaptive, п.п. |
|---|---:|---:|---:|---:|---:|
| Стабильное качество | 90.972 | 89.583 | 89.583 | −1.389 | 0.140 → 0.140 |
| Сбой alfa/payflow, затем восстановление | 85.556 | 85.000 | 86.528 | +0.972 | 0.420 → 0.700 |
| Продолжительный сбой alfa/payflow | 78.056 | 79.028 | 82.500 | +4.444 | 0.420 → 0.420 |

Изолированный эффект обучения относительно `fixed`: 0, +1.527 и +3.472 п.п. соответственно; разницы считаются до финального округления. В этих прогонах отдельные recovery probes не сработали: ответы продолжали поступать через обычную балансировку. Поэтому выигрыш нельзя приписывать механизму probes; его ограничения проверяются отдельным тестом.

Конкретный пример, seed 404, продолжительный сбой: в заключительной фазе исходный balanced выбирает payflow первым для 22 из 40 alfa-операций, адаптивный — для 11. Для здорового банка в той же фазе адаптивный продолжает выбирать payflow: 28 из 40. Провайдер не блокируется целиком из-за одного проблемного сегмента.

Стабильный сценарий — проигрыш исходному balanced, а не скрытая победа. У fixed и adaptive здесь одинаковый результат: различие с balanced объясняется не одним только обучением, поскольку профили отличаются весами и оценкой prior. Трёх seed недостаточно для статистического вывода о преимуществе.

### Как выбиралась текущая версия

Это не единственный заранее зафиксированный эксперимент. На разработочных последовательностях обнаружилось, что слишком слабый вес долей даёт большой перекос. Повышение веса уменьшило его, но оставило лишние изменения в стабильном сценарии. После этого добавлен порог подтверждённого ухудшения; seed 404/505/606 впервые использованы после выбора этой логики. Исправление суммарного времени ответа проверено повторным запуском на этих же seed. Это ограниченная контрольная проверка, не доказательство обобщения на скрытый набор организаторов.

## Запуск адаптивного профиля вне лаборатории

```bash
bin/pulseproof run --policy config/adaptive.json --decisions outputs/adaptive-decisions.json --report outputs/adaptive-report.json
bin/pulseproof stream --policy config/adaptive.json --outcomes examples/runtime_outcomes.json < examples/runtime_events.jsonl
```

Первая команда по умолчанию использует выбранную локальную очередь и детерминированный симулятор ответов. Вторая — явно заданную ленту ответов. Реальных платежей обе не отправляют. Профиль сдачи `balanced` и браузерный replay автоматически не переключены: нет основания заменять их профилем, который пока не превосходит baseline во всех проверках.

## Ограничения и следующий критерий допуска

- Состояние обучения — в памяти одного процесса; нет восстановления после рестарта, общей модели нескольких экземпляров или банковского коннектора.
- Параметры окна, затухания, сегментов и порога заданы в конфигурации, а не автоматически найдены по реальным данным. Редким сегментам может не хватить наблюдений.
- Затухание может ослабить сигнал даже без подтверждения восстановления; моментальное безопасное восстановление не доказано.
- Детерминированные проверки не дают несмещённую оценку другой политики. Исторические логи выбранных провайдеров сами по себе не доказывают причинный прирост конверсии.
- Лаборатория не моделирует реальную корреляцию банковских сбоев, сложные задержки, стоимость повторов и тяжёлые распределения сумм. Brier измерен на выбранных действиях разных политик и не является чистым сравнением калибровки на общем наборе.
- Это не Thompson sampling/UCB и не алгоритм с доказанной границей regret. Называть его так было бы неправильно.

Перед включением по умолчанию нужны независимые серии с редкими сегментами, меняющимися снимками, задержками и ёмкостями; заранее заданные допустимые отклонения по долям и цене повторов; затем проверка на разрешённой организаторами ленте статусов. До этого заявляем реализованную онлайн-адаптацию и воспроизводимые синтетические результаты, а не production-ready платёжную систему.

## Основания выбора подхода

Контекстная маршрутизация с обновлением по результатам и учётом запаздывающих ответов применяется в [Hyperswitch Intelligent Routing](https://docs.hyperswitch.io/about-hyperswitch/payments-modules/intelligent-routing). Проблему частичной обратной связи и корректного сравнения политик разбирает [исследование Microsoft по offline evaluation contextual bandits](https://www.microsoft.com/en-us/research/wp-content/uploads/2016/02/paper-7.pdf). Это основания для архитектурных ограничений, а не свидетельство идентичности нашего алгоритма или его качества.
