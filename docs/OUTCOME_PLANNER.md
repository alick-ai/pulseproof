# Роутинг по последствиям каскада

Реализован отдельный профиль `config/planner.json`. Он заменяет итоговое ранжирование провайдеров оценкой каскадов, но сохраняет HardGate, учёт долей, Ledger и действующий протокол поздних статусов. Это не подключённая банковская система и не доказанный оптимальный онлайн-алгоритм.

**Профиль сдачи по умолчанию — `config/balanced.json`, не planner.** Экспериментальные результаты и объяснения записываются отдельно. Публичный валидатор не принимает конкретный вероятностный каскад op_104 (28/29), хотя он проходит независимую проверку runtime; на явно объявленной симуляции без отказов получается 29/29. Совместимость со скрытым валидатором неизвестна. Эти два вида проверки нельзя смешивать или выдавать симуляцию `approve` за качество обработки отказов.

Короткий показ начинается с запрета `op_103 → vipay`, затем с обратной задачи для op_101 и только потом с таблицы альтернатив: [JURY_DEMO.md](JURY_DEMO.md).

## Запустить и увидеть решение

Из корня репозитория:

```bash
bin/pulseproof run --policy config/planner.json --decisions outputs/planner-decisions.json --report outputs/planner-report.json
bin/pulseproof validate --policy config/planner.json --decisions outputs/planner-decisions.json --report outputs/planner-report.json
bin/pulseproof explain op_101 --decisions outputs/planner-decisions.json --report outputs/planner-report.json
```

Первый запуск использует выбранную локальную очередь и симулятор ответов. Отдельные пути результатов не перезаписывают обязательные файлы сдачи. Для публичного op_101 расчёт показывает альтернативы с payflow, vipay и quickpay первым, ожидаемые конечные вероятности и вклад каждого фактора в разницу оценок. Порядок может меняться при новых входах и правилах; это не зашитый выбор.

### Отдельно: совместимость с публичным скриптом организаторов

Публичный `validate_10.rb` безусловно требует quickpay для op_104. В вероятностном прогоне quickpay может отказать, после чего корректный fallback даёт 28/29 у публичного скрипта, хотя независимая проверка подтверждает правильность каскада. Это ограничение публичной проверки, не основание подделывать исход или запрещать fallback.

Для проверки структуры/маршрутов в сценарии без отказов используется **явно объявленный** симуляционный режим:

```bash
bin/pulseproof run --policy config/planner.json --simulation-mode approve --decisions outputs/planner-public-decisions.json --report outputs/planner-public-report.json
ruby scripts/validate_10.rb outputs/planner-public-decisions.json
```

Режим отражён в policy/hash/снимках и аудите отчёта. Его результаты нельзя использовать как доказательство успешности или устойчивости при отказах; для этого предназначены тесты runtime и plan-lab с независимыми исходами. Основные файлы сдачи и balanced по умолчанию не изменены.

Потоковый режим с явно заданными симулированными ответами:

```bash
bin/pulseproof stream --policy config/planner.json --outcomes examples/runtime_outcomes.json < examples/runtime_events.jsonl
```

## 1. Сравнивается каскад, выполняется только первый шаг

HardGate исключает запрещённые и уже отказавшие маршруты. Для каждого допустимого первого провайдера `CascadeOptimizer` строит оптимальное продолжение **внутри текущей замороженной аддитивной модели**. Перестановки не перебираются и не отрезаются по бюджету: больше нет зависимости от случайного префикса порядка входных провайдеров.

Пусть `a_i` — взвешенная локальная стоимость попытки i, а `f_i` — вероятность продолжить после неё. Поменяв соседние i и j, получаем сравнение:

```text
i → j: a_i + f_i × a_j
j → i: a_j + f_j × a_i

i перед j не хуже, когда
a_i × (1 − f_j) ≤ a_j × (1 − f_i)
```

Стоимость оставшегося продолжения одинакова для обоих порядков: его вероятность достижения умножается на один и тот же `f_i × f_j`. Это даёт точное попарное правило для данной модели. При `f < 1` оно соответствует порядку по `a / (1 − f)`, но реализация сравнивает произведения без деления и отдельно корректно обрабатывает нейтральные действия, ничьи и недостижимый хвост. Числа модели переводятся в `Rational`: сравнение точно для экспортированных конечных коэффициентов, а не для неизвестных истинных вероятностей. Отображаемые стоимости округляются отдельно.

Строится одно лучшее продолжение на каждое из n первых действий. Консервативная верхняя оценка сложности текущей канонической реализации — `O(n³)` для одной цепочки и `O(n⁴)` для всех фиксированных первых действий, вместо факториального перебора. Это не обещание времени полного роутера: оценка дефицита ресурса и подготовка доказательств имеют собственную стоимость.

Для трёх внешних провайдеров `chains_evaluated` теперь равно 3, а не 6. Поле `all_external_orders_evaluated: false` означает, что все перестановки **не перечислялись**, а не что минимум приближённый. За гарантию отвечает отдельное поле `optimization.exact_for_frozen_model: true`, метод — `exact_pair_exchange`. Замороженные локальные коэффициенты сохранены в `cascade_model`, чтобы расчёт можно было повторить.

Self-provider добавляется только последним и только если допускается текущими hard-правилами. План никогда не даёт ему первое место при наличии внешних кандидатов.

В условной модели для провайдера i:

```text
r_i                 = вероятность дойти до попытки i
p_i                 = оценка принятия при терминальном ответе
t_i                 = заданная вероятность неизвестного/pending результата
P(принял i)         = r_i × (1 − t_i) × p_i
P(pending на i)     = r_i × t_i
r_(i+1)             = r_i × (1 − t_i) × (1 − p_i)
ожидаемые попытки   = сумма r_i
```

Pending — остановка каскада до подтверждённого статуса, не скрытый reject. Вероятности принятия, pending и полного отказа суммируются в единицу. Это расчёт для текущего замороженного снимка, с условно независимыми исходами попыток. Реальные зависимые банковские отказы могут нарушать предпосылки.

### Отдельный сертификат зависимости

Рядом с каждым планом теперь хранится `dependence_certificate`: при нулевом pending он даёт достижимые границы Фреше успешности при заданных маргиналах и произвольной зависимости. На публичном op_101 независимый полный отказ ≈ 0.063505%, границы — 0–10%; нижнюю границу успеха 90% определяет fallback. Это не доверительный интервал для истинных вероятностей и не гарантия реальных выплат. При любом ненулевом pending возвращается `not_applicable`, без неподходящих границ.

Сертификат аналитический: он не меняет роутинг и **не доказывает оптимальность порядка при неизвестной зависимости**. Уже существующие члены попыток, задержки, атрибуции и бизнес-штрафов зависят от prefix-reach. При t = 0 и одинаковом составе инвариантен член полного отказа (а при fallback последним — также вероятность его достижения); это не инвариантность всей цели. При pending может меняться `unresolved_or_failed`, а при изменении состава — и полный отказ. Регрессионный тест сохраняет контрпример переворота порядка с теми же маргиналами.

`explain` проверяет данные до печати. Независимый `DependenceVerifier` восстанавливает границы через пересечение отказов, не вызывает производителя или оптимизатор и отклоняет подмену дробей, Float-значений и области гарантии. Точная постановка, численная область и покрытие: [DEPENDENCE_CERTIFICATE.md](DEPENDENCE_CERTIFICATE.md).

Исполняется только первый шаг. После подтверждённого отказа заново выполняются HardGate и планирование по актуальному состоянию. Будущая часть рассчитанной цепочки не является обязательством её выполнить. Тест меняет правила во время pending и подтверждает, что старый план не обходит новое отключение провайдеров.

## 2. Целевая функция прозрачна

Оценка включает ожидаемое изменение квадратичного долга count/volume, число попыток, задержку, условные рубль-секунды pending, вероятность неразрешённого/неуспешного результата, обращение к fallback, стресс-оценку дефицитной ёмкости и заданные бизнес-факторы.

Для count-долга d принятие одной операции меняет квадрат долга на `1 − 2d`. Планировщик усредняет это изменение по конечным провайдерам каскада, а не начисляет весь ожидаемый результат первому провайдеру. Pending получает только предварительный зачёт, согласованный с резервированием; фактическая конечная доля продолжает считаться по результатам исполнения. Для объёма используется аналогичная формула с суммой, нормированной на средний уже увиденный чек.

Компоненты и веса сохраняются отдельно в `outcome_plan.raw_metrics`, `terms`, `objective`. У альтернатив есть `gap_to_best` и `alternative_terms_minus_best`: видно, чем именно проигрыш по одним факторам компенсируется выигрышем по другим. Отрицательное изменение долга допустимо: оно означает улучшение баланса.

Веса — явная бизнес-настройка, не найденный универсальный оптимум. Рубли, секунды и доли не объявляются одной «реальной денежной стоимостью»: коэффициенты переводят их в условную целевую функцию. Прежний ограниченный контроллер долга и его насыщение сохранены; это не жёсткая гарантия конечных долей. `DeficitController` ведёт долг, но не назначает итогового провайдера до планировщика. HardGate ограничивает допустимость; count/volume остаются мягкими целями внутри выбора.

Чувствительность отдельно перепроверена **после перехода на точный решатель**, через настоящий RuntimeSession и проверку итогового отчёта, на публичной очереди при одинаковых успешных ответах. Изменение только веса `count_potential_change` с 0 на 0.6 и 0.8 снова дало распределения vipay/payflow/quickpay 3/2/5, 3/3/4 и 4/3/3, а count-L1 — 50, 30 и 10 п.п. Planner с 0.6 здесь уступает balanced (10 п.п.) по конечным долям. Это не эффект случайных отказов и не «доли уже зафиксированы»: целевая функция меняет назначения.

Конверсия используется непосредственно в вероятностях: значения 10% и 30% больше не превращаются в одинаковый обрезанный штраф. Дополнительный haircut по неопределённости есть в настройках, но по умолчанию равен нулю и не заявляется доверительной границей.

## 3. Две скорости памяти и объединение редких сегментов

В planner-профиле вчерашняя история не затухает за пять минут. Она формирует медленный prior с периодом полураспада семь дней. Текущие подтверждённые ответы образуют отдельное быстрое окно из последних 40 наблюдений сегмента с периодом полураспада пять минут.

Историческая строка входит ровно один раз: с весом 1 для точного контекста, 0.35 для другого контекста того же банка или 0.1 для другого банка того же провайдера. Затем применяется возрастной вес и prior текущего снимка. Это явно заданное объединение данных, не точная иерархическая байесовская модель. Онлайн-ответ не добавляется одновременно в медленную историю и быстрое окно.

Медленный prior фиксируется на загруженной истории и обновляется с изменением времени/снимка; полноценное долгосрочное переобучение и долговечное хранение не реализованы. Отсутствующий или несовместимый контекст не получает выдуманных меток. История служит оценкой, а не доказательством результата другого провайдера.

На публичном снимке op_101 историческая эффективная масса для vipay теперь около 5.30, payflow 2.49, quickpay 3.53 вместо практически нулевой массы старого быстрого окна. Эти числа — веса, не количество независимых экспериментов.

## 4. Общая ёмкость и проверенные изменения лимитов

OpportunityModel строит ограниченную ленту из уже известных форм операций, без доступа к будущей очереди. В копиях состояний совместно расходуются лимиты всех провайдеров: это позволяет обнаружить нехватку общей ёмкости даже когда у каждой формы есть несколько маршрутов.

Для каждого возможного назначения текущая выплата условно резервируется; сравнивается обслуженная часть исторической стресс-ленты до и после резерва. Используются два порядка ленты и жадное размещение с обычным HardGate. Это **не точный max-flow/MILP, не доказанная теневая цена ресурса и не прогноз числа потерянных выплат**. Текущий гипотетический резерв держится весь горизонт, синтетические последующие операции сразу подтверждаются. RPM и существующие резервы учитываются. Прогноз может быть избыточно консервативным.

В отчёте сохранены лента, размер выборки, `served_before`, `served_after_reservation`, `lost_service_slots`. Неудачные попытки также создают нагрузку, поэтому стоимость агрегируется по вероятности достижения каждого шага; возможен повторный учёт взаимосвязанных потерь — это эвристика.

Рекомендации перебирают заданные увеличения дневного лимита на копии того же состояния и повторяют стресс-прогон. Возвращается минимальный улучшающий шаг **среди проверенных**, исходное и предлагаемое значения, количество обслуженных операций до/после. Если ни один шаг не помогает, рекомендации нет. Настоящая конфигурация не меняется. Увеличение договорного лимита требует решения оператора.

Тест: при нулевой дневной ёмкости и чеках 2000 шаг +1000 не помогает, +2000 обслуживает одну операцию; выбирается +2000, а не шаблонное «увеличить лимит». Другой тест показывает потерю одного общего слота при трёх взаимозаменяемых провайдерах — без единственного эксклюзивного маршрута.

## 5. Проверка объяснений и безопасности

PlanVerifier не вызывает CascadeOptimizer. Он самостоятельно проверяет рациональные попарные неравенства и канонические ничьи каждого продолжения при фиксированном первом действии; порядок альтернатив сверяется по точной стоимости, а не по округлённым отображаемым оценкам. Из полной модели заново агрегируются raw-компоненты, взвешенные terms и objective.

Локальные вероятности, задержки, count/volume-цели, pending-удержание, fallback и бизнес-штрафы независимо сверяются с сохранённым снимком. Тесты с подменой вероятностей, локальных коэффициентов и продолжения не проходят. Так сертификат проверяет не только красивую сумму рядом с цепочкой, но и допустимость заявленного оптимума внутри модели.

Ограничение сохраняется для scarcity: проверяется согласованность с опубликованными `served_before`, `served_after_reservation`, размером стресс-ленты и `lost_service_slots`, но полная историческая стресс-симуляция не запускается заново. Это не независимое доказательство истинности вероятностей, истории или качества стресс-распределения. HardGate/резервы/итоговые состояния отдельно проверяет существующий AuditReplay.

Математический оптимизатор проверяется отдельно: на 40 случайных моделях с 2–6 внешними провайдерами результат и каждое принудительно выбранное первое действие сверяются с полным перебором; также есть модель с 64 провайдерами и известным оптимумом. Эти тесты проверяют реализацию правила, не достоверность прогнозируемых банковских ответов. Актуальный итог полного набора получать через `rake test` после сборки версии.

Также проверяются: отсутствие повторного обучения на дубле статуса; запрет каскада до разрешения timeout; перепланирование после смены правил; неизменность доказательства префикса при разных последующих операциях; отсутствие мутации реальных состояний при гипотетических расчётах.

## 6. Обратная задача: что должно измениться, чтобы выбрать другого

```bash
bin/pulseproof challenge op_101 --prefer vipay --factor count_potential_change --human --report outputs/planner-report.json --challenge-output outputs/challenge-op101.json
bin/pulseproof challenge op_103 --prefer vipay --human --report outputs/planner-report.json
```

Обратная задача использует сохранённую **модель локальных действий**, а не считает прежние лучшие цепочки достаточной матрицей для всех новых настроек. Изменение веса способно поменять не только первого провайдера, но и оптимальное продолжение. Поэтому `PolicyChallenge` заново оптимизирует всю цепочку при каждом проверяемом весе.

Для одного изменяемого коэффициента каждое попарное сравнение становится аффинной функцией веса. Все неотрицательные точки пересечения делят `[0, ∞)` на границы и открытые промежутки. Внутри каждого промежутка порядок попарных предпочтений неизменен. Канонический точный оптимизатор проверяет границы отдельно от промежутков, поэтому ничья на границе не выдаётся за победу в соседнем интервале.

Ответ содержит выигрышные области с открытыми/закрытыми концами, ближайшую границу, проверенное представимое значение веса, исходную и новую цепочки. Предложенный вес ещё раз проходит точную оптимизацию на той же модели; выбирается ближайшее допустимое машинное значение, а не заранее заданный шаг `10⁻⁶` внутрь интервала. На текущем публичном op_101 нижняя граница открыта; её десятичное отображение — **0.7985512111061964**, проверенный вес — **0.7985512111061965**. Соседний меньший Float всё ещё выбирает payflow, а предложенный уже выбирает vipay. Отдельный тест подтверждает это настоящим Router на том же начальном состоянии. Точная рациональная граница и точные стоимости остаются в JSON; близкие стоимости могут одинаково выглядеть после округления и при этом не быть ничьей.

`--human` показывает короткий русский разбор с полными десятичными значениями весов, открытостью концов и результатом соседнего машинного веса. Без флага по умолчанию выводится прежний машинно-читаемый JSON; `--challenge-output` независимо сохраняет его в файл. Человеческий вывод не подменяет вычисление и не печатает длинные рациональные дроби. При обновлении входов число переключения вычисляется заново.

Точность относится к одной неотрицательной настройке и экспортированным коэффициентам **того же снимка**. Это не лучшие настройки на весь день, не оптимальность одновременно по нескольким параметрам и не прогноз улучшения конверсии. Модельные вероятности и предпосылка аддитивности остаются ограничениями даже при точном решении математической задачи.

Для op_103 vipay отсутствует среди допустимых первых действий: возвращается `not_eligible`, а не рекомендация увеличить его вес. Если одного параметра недостаточно, возвращается `no_single_weight_solution`. Ни один режим challenge не отправляет выплату и не меняет конфигурацию.

Полный публичный walkthrough для подготовки до выступления:

```bash
rake jury
```

Он запускает тесты, вероятностную симуляцию, разбор альтернатив, допустимую и недопустимую обратные задачи, затем отдельно проверяет формат на явно обозначенной симуляции без отказов. Результаты остаются в `outputs/`, обязательные файлы сдачи не подменяются. На сцене достаточно коротких `challenge` и `explain` над уже подготовленным отчётом; это вычисления на сохранённом снимке, а не воспроизведение всего стенда. Повторное сравнение большого стенда запускается заранее командой ниже.

## Сравнительный стенд

```bash
bin/pulseproof plan-lab --lab-seeds 713,947,1201 --lab-output outputs/planner-exact-holdout.json
```

Пять сценариев: стабильность, локальный сбой с восстановлением, длительный сбой, банковская специализация, давление на ёмкость. Четыре политики: balanced, предыдущая adaptive, planner без онлайн-обучения, полный planner. По 120 операций, одинаковые потенциальные ответы операция/провайдер; каждая политика получает только фактически выбранный ответ. В каждой серии 120 синтетических исторических записей предыдущего дня. Все прогоны проходят независимую проверку.

Разработочный seed 11 использован до контрольных 713/947/1201. Параметры целевой функции после первого сравнения не подгонялись. Это ограниченный синтетический эксперимент, не статистическое доказательство бизнес-прироста. Банковские ограничения сняты в стенде для сравнимости, а ёмкости искусственно заданы; публичные данные проверяются отдельно.

Стенд повторён с точным решателем: 60 прогонов (пять сценариев × три seed × четыре политики), каждый прошёл независимую проверку. Во всех 20 сочетаниях сценарий/политика четыре нетайминговых показателя — успешность первой попытки, попытки на выплату, count-L1 и fallback — точно совпали с прежним `outputs/planner-holdout.json`. Новый результат сохранён отдельно в `outputs/planner-exact-holdout.json`. Это повторная проверка на тех же seed, не новая независимая выборка.

Это эмпирическое совпадение на данной семье потоков, а не гарантия неизменного распределения и не доказательство отсутствия компромисса качество/доли. Контрпример с изменением веса на публичной очереди приведён выше. В банковской специализации число попыток на выплату снизилось с 1.2278 у adaptive до 1.1111 у planner. Стабильность и давление на ёмкость не показали преимущества новой политики — эти результаты не скрываются.

Большая часть выигрыша в специализации уже есть у замороженного planner: его медленный контекстный prior и постановка выбора отличаются от adaptive. Поэтому нельзя приписать все +9.44 п.п. онлайн-обучению или отдельно поиску каскада. Для такого вывода нужны дополнительные ablation-сравнения каждого компонента. Изолированное сравнение обучения — planner против planner_frozen.

Измерение локального времени включает расчёт модели, копирование состояний и формирование доказательств, но исключает финальный отчёт; это не банковская задержка и не SLA. Новый стенд выполнялся параллельно с тестами: влияние конкуренции за ресурсы не отделено, поэтому время нельзя использовать как чистое сравнение скорости старой и новой версии. Устранён факториальный перебор, но ускорение всего движка **не доказано**; рациональная арифметика, стресс-модель и доказательства имеют собственную цену. Полные результаты по seed, вычислительные задержки и фазы доступны в `outputs/planner-exact-holdout.json`. Полный стенд запускать до выступления.

Это локальный результат, не подтверждение скрытой оценки или готовности к банковской эксплуатации; для локального Git-состояния двух обязательных JSON есть отдельный read-only `rake submission_git`.

## Что намеренно не заявляется

- Не обеспечено превосходство во всех режимах; новый профиль не заменяет автоматически balanced для сдачи.
- Браузерный replay не переписан и по умолчанию не показывает новый профиль; смотреть расчёты нужно через команды выше.
- Нет банковского коннектора, restart recovery, распределённых транзакций и долгосрочного хранилища обучения.
- Вероятности pending должны быть заданы отдельно; при отсутствии данных в профиле это нули, а не оценка нулевого риска. `conversion_24h` используется как prior условного принятия — его реальная семантика потребует калибровки при интеграции.
- Задержки прогнозируются по `avg_latency_sec` снимка, а не по полноценной модели хвоста задержек. Рубль-секунды здесь условная мера резерва, не стоимость денег.
- Нет внешнего сервиса принятия решений и просмотра будущей тестовой очереди.
