# Повторный технический разбор PulseProof

Дата: 4 сентября 2026. Это аудит реально имеющегося кода, а не обещание победы или готовности к промышленной эксплуатации.

## Главный вывод

Предыдущая версия была глубже обычного макета, но её демонстрация и описания опережали проверенные возможности. Десять публичных операций и зелёный публичный валидатор не подтверждали корректность поздних статусов, обновления правил, денежных границ и аналитики. Несколько принципиальных проблем воспроизведены отдельными тестами и исправлены.

Сдаваемый продукт — запускаемый Ruby-движок, который формирует два проверяемых JSON. Панель — дополнительный просмотр результата, не сам алгоритм. Для инженерной защиты сильнее показывать воспроизводимый сложный сценарий и независимую проверку, чем заявлять «самый умный роутинг» без эксперимента.

## Дополнение: регрессия локали и ложная готовность сдачи

После добавления CLI-тестов воспроизведены 2 failures и 1 error при незаданных `LANG`, `LC_ALL`, `LC_CTYPE`: Ruby выбирал US-ASCII, а тесты сравнивали прочитанный отчёт и перехваченный вывод с UTF-8-строками. Исправлены явное UTF-8-чтение и декодирование захваченных байтов; глобальные настройки Ruby не менялись. В обычный набор добавлена проверка CLI в отдельных процессах с пустой, C, POSIX и UTF-8-локалью.

Финальный набор: 196 тестов / 6334 assertions без ошибок; CLI-регрессии внутри него проверяют пустую, C-, POSIX- и UTF-8-локаль. Полный release также проверяет исполняемую матрицу требований 31/31, публичный валидатор 29/29, privacy, Ruby-majority (75.0%), lint и сборку; после финального коммита он повторяется командой `rake arm_stopcode`. Исторический прогон ниже описывает более раннюю версию и не заменяет эти результаты.

Отдельно устранено смешение локальной генерации и сдачи. Обе команды `submit` теперь печатают `GENERATED_LOCALLY`, а не `READY`; `submission_layout` проверяет только локальную раскладку. Read-only `submission_git` требует реальный HEAD на main, оба обычных JSON в его корне, совпадение с индексом и рабочими байтами, затем валидацию относительно выбранной тестовой очереди. Публикация, полнота исходников и подлинность очереди не выводятся из этой проверки.

Критический путь stopcode отделён от проверок, не зависящих от новой очереди. `rake arm_stopcode` заранее выполняет полный `release` и создаёт игнорируемую квитанцию, связанную с точным чистым коммитом `main`, его деревом, версией Ruby, tracking-ref и совпавшим во время проверки удалённым `origin/main`. После появления очереди `rake stopcode` разрешает отличаться только самой очереди и двум обязательным выходным JSON, затем выполняет маршрутизацию, строгий валидатор, PII, Ruby-majority и раскладку. Это перенос уже выполненной работы, а не удаление проверки: изменение исходников блокирует быстрый путь. Доступность и состояние remote после момента предварительной проверки всё равно подтверждаются отдельно.

Исходный код зафиксирован в ветке `main` и опубликован в приватном удалённом репозитории. Выданной организаторами stopcode-очереди пока нет, поэтому финальную проверку `submission_git` корректно выполнить ещё нельзя. Проверка имени `operations_queue_test.json` сама по себе не устанавливает происхождение файла.

## Где фактически оценивают решение

За час до стопкода организаторы выдают `operations_queue_test.json`. Код обрабатывает его и размещает `routing_decisions_test.json` и `routing_report_test.json` в корне ветки `main`. По тексту задания отсутствие/ошибка имени/пути/структуры считается неприкреплённым результатом. Для закрытой очереди ожидается аналогичный, но не обязательно идентичный публичному, валидатор.

| Техническая категория | Баллы в задании | Что надо доказать кодом |
| --- | ---: | --- |
| Обязательные файлы | 40 | Правильная очередь, полное покрытие, имена и структура |
| Гибкость правил | 32 | Count, volume, priority, amount, conversion, load; конфигурация |
| Базовая корректность | 22 | Hard/soft, изменение состояния, каскад и fallback |
| Согласование целей | 15 | Формальный выбор и поведение при недоступной цели |
| Аналитика | 11 | Реальные доли, причины отклонений, конкретные рекомендации |
| Объяснимость | 10 | Причины выбора/отказа и порядок попыток |
| Техническая реализация | 10 | Структура, запуск, ошибки и границы |

Это 140 технических баллов плюс 20 отраслевых. Отдельная экспертная оценка чекпоинтов — 100 баллов, это другая таблица, не её замена. Дополнительные идеи в отраслевой таблице дают 6 баллов; необычность не заменяет работоспособность обязательной части.

`simulated_result` допускает симуляцию. В материалах не предоставлены реальные API банков, ключи или sandbox-контракты. Поэтому требовать настоящего перевода для конкурсной сдачи из этих материалов не следует, но выдавать симулятор за подключённый платёжный сервис тоже нельзя.

## Что было поверхностным и что изменено

| Проверка | Было | Теперь |
| --- | --- | --- |
| `0.1 + 0.2` при лимите `0.3` | Допустимый платёж отклонялся из-за float | Накопление денег и сравнение ёмкости в целых копейках |
| Смена traffic 40% → 10% | Контроллер сохранял старую цель | Цели обновляются на следующей операции |
| Изменение conversion | Старое значение в метрике | Новый snapshot входит в пересчёт prior и снимок решения |
| Повтор operation_id | Повторный заход ломал переход состояния | Тот же payload возвращает результат; другой payload отклоняется без новой отправки |
| Поздний статус после других выплат | Поддерживалась только немедленная симуляция resolution | `Router#reconcile` продолжает одну pending-операцию на свежем состоянии |
| Статус старой попытки | Корреляция только по operation_id | Проверка operation + provider + attempt + идентификатор события |
| Timeout → approved | Решение расходилось с собственным валидатором | Хранятся первичный result и подтверждённый resolution |
| Исключение сетевого timeout | Резерв оставался, вызов аварийно завершался | Неопределённость возвращается как pending без запуска каскада |
| Проверка отчёта | Подменённый дневной оборот проходил | Суммы/доли/исходы/резервы сверяются с решениями и независимым replay |
| Историческая калибровка | Несовместимые строки лишь помечались; продолжали влиять | Из калибровки исключены несовместимые и ещё не известные на снимке исходы |
| Цель объёма в balanced | Придуманные 45/10/45 применялись как штатная цель | Нет цели без данных/явной конфигурации; отдельные профили остаются примерами |
| Shadow-сравнение | У стратегий были разные проверки лимитов | Общие Router/HardGate/Ledger, независимое состояние каждой стратегии |
| «Точный оптимум» | Поиск пропускал часть hard-правил и мог резко разрастись | Общий HardGate, ограничение узлов; точность заявляется только для завершённого статического count-only поиска |
| Proof Capsule | В основном hash без полного контекста попытки | Хранятся очищенный снимок, правила, метрики, политика, долг, резервы; hash привязан к событию резервирования |

Тесты: `adversarial_runtime_test.rb`, `runtime_session_test.rb`, `metric_calibration_test.rb`, `feasibility_envelope_test.rb` и существующие проверки движка. Первые шесть adversarial-проверок до исправления дали три failure и три error — это были реальные дефекты, не только возможные улучшения.

## Что именно делает алгоритм

1. Отсекает недопустимых провайдеров по hard-правилам.
2. Начисляет целевую долю текущей операции в долг count/volume. Будущая очередь не передаётся Router.
3. В balanced сравнивает кандидатов по максимальному нормированному отклонению count/volume после назначения. Затем учитывает взвешенные штрафы качества и бизнес-факторов; последний tie-break детерминирован.
4. До вызова адаптера резервирует деньги и ёмкость и даёт провайдеру предварительный зачёт доли.
5. Approved фиксирует сумму; reject/cancel освобождает резерв и возвращает зачёт; timeout сохраняет резерв до подтверждения.
6. При позднем отказе следующий кандидат выбирается из актуального состояния, без второго начисления операции и без перезаписи соседних решений.

Это детерминированная эвристика, не доказанный оптимальный онлайн-алгоритм. Долг ограничивается для управления, но необрезанный `raw_count_debt`/`raw_volume_debt` отдельно показывает исходное отклонение. Компенсации управленческого долга после насыщения не являются математическим откатом всей истории.

`redistribute_unavailable: true` — отдельный, по умолчанию отключённый режим перераспределения текущей цели среди доступных провайдеров. Он меняет политику, а не делает исходную бизнес-цель «достигнутой». Параметры весов, amount bands, prior и recovery — явно выбранные настройки, не подтверждённый оптимум для скрытого распределения.

Приоритет качества в balanced вторичен относительно цели долей. Если бизнес требует иного компромисса, нужно явно выбрать/настроить `weighted_sum` или `conversion_first`, а не объявлять один профиль универсально лучшим.

## Что демонстрировать вместо обещаний

```bash
rake test
bin/pulseproof run --queue data/operations_queue_10.json
bin/pulseproof validate --queue data/operations_queue_10.json
ruby scripts/validate_10.rb routing_decisions_test.json
bin/pulseproof stream --policy config/cascade.json --outcomes examples/runtime_outcomes.json < examples/runtime_events.jsonl
```

Последний сценарий: A timeout → B approved → payflow отключён → cancel A/vipay/1 → A продолжает каскад на quickpay → старый approved A/vipay/1 игнорируется → отчёт независимо проверяется. Встроенный отчёт использует оригинальные операции и snapshot плюс журнал; одного журнала недостаточно для восстановления всей аналитики.

Публичная очередь даёт 4/3/3 операции против целей 40/35/25. L1-ошибка долей — 10 п.п. Count-only hindsight-поиск тоже находит 10 п.п. Это объяснимо в том числе дискретностью десяти операций. Равенство этому небольшому частному оптимуму не доказывает лучший routing на скрытой очереди или преимущество по конверсии.

## Чего пока нет — не скрывать на защите

- Реальных интеграций с провайдерами и подтверждения исходов из их API. Поставляемые approve/scripted/deterministic исходы — симуляция.
- Долговечного хранилища состояния, восстановления после рестарта, transactional outbox и координации нескольких процессов. Mutex и идемпотентность действуют в одном экземпляре Router.
- Полного протокола применения внешних финансовых снимков. Нужны версия/watermark и правила сверки, чтобы не удвоить резерв. Прямое изменение ledger-owned balances запрещено.
- Автоматического перехода между банковскими днями, фонового status polling и очереди отложенной обработки при недоступности даже fallback.
- Статистического доказательства улучшения бизнеса на неизвестном потоке. Shadow-график с одной очередью и seed — иллюстрация, не эксперимент достаточной мощности.
- Гарантии отсутствия двойной выплаты во внешней банковской сети. Противоречивые ответы провайдера требуют операционной сверки; локально запоздалый ответ не перезаписывает другую попытку.
- Независимой внешней подписи журнала: SHA-цепочка сама по себе не доказывает подлинность источника.

Следующий качественный этап — согласовать lifecycle контракт внешнего snapshot/status, добавить durable execution и прогнать набор независимых сценариев с заранее выбранными метриками. Для конкурсной сдачи первоочередны корректные обязательные файлы, прозрачная политика и воспроизводимость уже реализованного поведения.

## Фактическая проверка после изменений

`rake release` завершён успешно 4 сентября 2026:

- Ruby: 51 тест, 216 assertions, 0 failures/errors/skips.
- Публичный валидатор организаторов: 29/29, без ошибок и предупреждений.
- Строгий валидатор, пересборка журнала и проверка чувствительных значений — пройдены.
- Проверка структуры файлов в корне `main`, lint и сборка веб-интерфейса — пройдены.
- Оценка доли исходных строк: 63.42% production Ruby; тесты и официальный валидатор в числитель не включены, CSS/HTML/config интерфейса включены в знаменатель. Это прозрачная локальная оценка, не обещание методики подсчёта жюри.
- Отдельный запуск JSONL-сценария дал A/vipay/expired → B/vipay/approved → A/quickpay/approved; старый статус проигнорирован; финально settled=2, pending=0, reserved=0.

Текущие корневые JSON рассчитаны **по публичным десяти операциям**, а не по скрытой стопкод-очереди. Сам код локально проверен; загрузка решения организаторам, коммит и публикация в удалённом репозитории этим запуском не выполнялись.
